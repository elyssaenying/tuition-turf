# Data contracts

Status: proposed schema version `0.1.0`; no tables are populated. Field names are an implementation contract, subject to explicit revision after source feasibility. Files below are planned outputs, not created datasets.

## Shared conventions

- Stable IDs are strings. Names are labels, never join keys. Business entities and geography have separate IDs.
- Dates use ISO `YYYY-MM-DD`; timestamps use ISO 8601 with UTC offset. Every analytical run has `run_id`, `schema_version`, `method_version`, `analysis_cutoff` and source-snapshot references.
- Counts are nonnegative integers when observed; allocated population proxies may be nonnegative decimals and must not claim exact-person precision. Money is numeric SGD; monthly and one-time amounts have distinct fields. Shares are in `[0,1]`; utilisation may exceed 1 to signal infeasibility. Distances are metres and travel times minutes.
- `null` means unknown/not available and requires a `missing_reason`/quality flag. Zero means measured or calculated absence. IDs, table-grain keys, statuses and lineage references are non-null. Use JSON `null`; disallow NaN and infinity. A field required for a comparison may be nullable during processing, but then blocks that comparison.
- Geometry exchange is GeoJSON in WGS84, coordinate order longitude/latitude; projected working geometry records a verified metric CRS. Persist boundary vintage. Simplification must preserve IDs/topology and have documented tolerance.
- Each table grain below is unique per run/snapshot as applicable. Foreign keys must resolve; many-to-many relationships use explicit bridge tables. Multi-snapshot tables include snapshot IDs in their unique key.
- Field provenance uses `observed`, `calculated`, `proxy` or `assumption`. A calculated result based on proxies/assumptions retains those dependency flags; `calculated` does not imply empirically observed. Category belongs to the field/value, not indiscriminately to an entire row.

## Audit and reference tables

| Table / grain | Required fields and types | Constraints |
|---|---|---|
| `sources` / source resource | `source_id:string`, `publisher:string`, `title:string`, `verification_status:unverified|accessible_unconfirmed|verified_usable|verified_limited|unavailable|rejected`, `url:string?`, `verified_at:datetime?`, `verification_note:string?`, `coverage_notes:string`, `licence_status:string` | Use exactly the declared six statuses. `accessible_unconfirmed`, `verified_usable` and `verified_limited` require an opened URL and recorded verification timestamp. `verified_usable` and `verified_limited` also require inspection of the relevant content/metadata. `unavailable` requires a recorded access attempt and timestamp; `rejected` requires a timestamp, rejection reason and the evidence reviewed. `unverified` requires `verified_at = null`. |
| `source_snapshots` / acquired version | `snapshot_id:string`, `source_id:string`, `retrieved_at:datetime`, `reference_period:string`, `checksum:string`, `storage_ref:string`, `boundary_version:string?` | Acquisition only after feasibility; storage reference must not leak local private paths into public exports |
| `runs` / execution | `run_id:string`, shared version/cut-off fields, `snapshot_ids:string[]`, `configuration_ref:string`, `generated_at:datetime` | Reproducible inputs/configuration; stochastic runs additionally record seed/draw count |
| `field_provenance` / field value or homogeneous field group | `provenance_id:string`, `table_name:string`, `record_key:string`, `field_name:string`, `evidence_kind:enum`, `source_snapshot_ids:string[]`, `input_refs:string[]`, `method_ref:string?`, `assumption_ids:string[]`, `quality_flags:string[]` | Observations need snapshots; calculations need inputs/method; assumptions need registered assumption IDs; proxies need method and limitations |
| `assumptions` / scenario parameter | `assumption_id:string`, `scenario_id:string`, `parameter:string`, `value:number|string|null`, `unit:string`, `rationale:string`, `evidence_refs:string[]`, `review_status:string`, `lower:number?`, `upper:number?` | Bounds use same unit; provisional or unset parameters must remain explicit |
| `quality_issues` / detected issue | `issue_id:string`, `run_id:string`, `table_name:string`, `record_key:string?`, `check_id:string`, `severity:enum`, `status:enum`, `details:string` | Severity `blocker`, `warning`, `info`; status `open`, `resolved`, `accepted_limitation` with documented rationale |

`record_key` is a canonical JSON object containing the table's named key fields; do not join composite keys by ambiguous text concatenation. Homogeneous field-group provenance requires a documented selector and identical derivation/source semantics for all selected values.

## Dashboard-ready static bundle

Planned format: UTF-8 JSON tables plus GeoJSON map layers and a JSON manifest. Internal working storage format will be selected after source/volume review. Every analytical export has `run_id` and links to field provenance. No placeholder result rows will be generated. Browser assets are a curated copy of validated processed outputs, not direct raw-data access.

For cash flow, month 0 records opening outflows, months 1 through the horizon record operations, and cumulative cash starts before external financing. `opening_cash_sgd` is the initial cash requirement `K + D`; `peak_cash_deficit_sgd` includes opening outflows and subsequent deficits, so they must not be added together. The maximum negative cumulative balance is floored at zero. Payback nulls distinguish not reached from not computable through `payback_status`.

Financial feasibility means operating break-even is attainable within modelled capacity, not that assumed enrolment demand or profitability is proven. A `conditional` node can be supported by a `screened_feasible` premises with an evidenced cost scenario, but it must list the remaining permission or landlord confirmation and must not be described as lease-ready. A fully `recommended` or lease-ready premises requires `verified_eligible`. Premises with `unresolved` status belong to `investigate`; `ineligible` premises are excluded. Export no more than three combined `recommended`/`conditional` nodes per recommendation scenario. Distinct rows for a node's premises must not be mistaken for independent location recommendations.

## Derived-field and release rules

`direct_competition_exposure` is the provisional primary Pareto competition field. It must incorporate confirmed and possible competitor branches in the relevant catchment and should adjust for distance and P1–S4 level overlap when source feasibility supports those inputs. Its exact formula is deferred; every value requires `direct_competition_exposure_method` and competition quality flags. `direct_branches_per_1000 = 1000 × direct_branches_confirmed / accessible_target_population` remains descriptive only and must not serve as the primary Pareto competition criterion; return null with reason for zero/unknown population or incompatible coverage. Transit reach uses an explicit resident-population denominator and routing method; preserve numerator/denominator in provenance. Financial formulas follow the methodology plan. Pareto criteria follow the decision framework, including incomplete-data handling. Node-level summaries must disclose how premises alternatives were selected.

Validate keys, types, units, nullability, references, eligibility and reconciliations before copying exports into `app/public/data/`. The manifest and every bundled table must agree on run/scenario/schema versions. Later schema changes require a decision-log entry, version change and corresponding producer/consumer updates. Raw and generated tables remain absent in this pass.
